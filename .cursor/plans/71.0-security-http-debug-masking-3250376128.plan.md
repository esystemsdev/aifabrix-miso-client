# TypeScript SDK: check and fix secret leakage in HTTP logs

## Scope

### In scope

- Implement the fix and permanent regression tests in this SDK; a report or tests alone do not complete the plan while a confirmed leak remains.
- Extend existing packaged and hardcoded sensitive-field defaults for `plaintext`, `value`, and `encryptionkey` where absent, retaining current case-insensitive normalization, recursive masking, and custom-config semantics.
- Unconditionally omit request and response bodies from HTTP diagnostic records for the actual security pathname, including supported controller base prefixes, in both production and `NODE_ENV=test` logging paths.
- Preserve safe method, URL, status, duration, size, correlation and header metadata; preserve existing diagnostic sanitization, outgoing payloads, returned plaintext and caller-visible errors.
- Add focused unit, production-path, loopback HTTP and authorized dev02 live-harness proof, plus a short update to existing logging documentation and the Unreleased changelog.

### Out of scope

- No new logging/sanitization framework, configuration switch, dependency, public API, encryption/delete wrapper, endpoint contract, error-object redesign or broad refactor.
- No consumer repository changes. Miso Controller and Dataplane adoption belong to their owners.
- The separate TypeScript `createErrorResponse` error-type issue remains unresolved by this plan.
- No version bump, publication, deployment, credential rotation, consumer upgrade or archive without separate human authority.

## Current evidence

Local metadata reports TypeScript SDK **5.2.0**; the earlier issue report mentions 5.1.0. `src/utils/sensitive-fields.config.json` already contains `encryptionkey`, `encryptionKey` and `secret`; existing substring matching covers `clientSecret`. `plaintext` and `value` are missing. The hardcoded/browser fallback in `sensitive-fields.loader.ts` also lacks `plaintext`, `value`, and `encryptionkey`.

`src/utils/http-client-audit.ts` builds the production debug context with request and response bodies. `src/utils/http-client.ts` independently includes both in `logTestAuditSignals` for `NODE_ENV=test`. `diagnosticMessage` and `extractRequestMetadata` already sanitize diagnostic errors/data before these sinks; retain that owner rather than introducing another sanitizer.

`LoggerService` builds the masked final `LogEntry`, emits it through `logger.on("log", ...)` when `emitEvents=true`, and returns before Redis, audit queue or HTTP delivery. This is the smallest safe live-capture mechanism. Because event mode bypasses HTTP payload enrichment/serialization, retain one existing loopback assertion with event mode disabled that inspects ordinary `/logs` delivery.

## Architecture alignment

- Existing owners remain authoritative: `DataMasker` and `sensitive-fields.loader.ts` for field defaults; `http-client-audit.ts` for production HTTP audit/debug construction; `http-client.ts` for test-mode parity; `LoggerService` for final masked records and event emission.
- Add at most one small shared route predicate in the existing HTTP logging utilities. Parse relative or absolute targets and match pathname segment boundaries equivalent to `(?:^|/)api/security(?:/|$)`, allowing controller base prefixes while rejecting `/api/security-other/` and security text found only in a query.
- No OpenAPI, controller route, database, UI, public type or public API change. SDK request, response and error contracts remain unchanged.

## Code reuse scan

- Reuse `normalizeFieldName`, `DataMasker.maskSensitiveData`, current recursive matching and packaged/fallback loaders; do not add aliases or a second matcher.
- Reuse `diagnosticMessage` and metadata sanitization for error text. The body guard supplements them at log construction and does not replace them.
- Reuse current Axios fixtures, `tests/e2e/controller-fixture.mjs`, `tests/manual/encryption-live.mjs`, and `LoggerService` event emission. Do not create another test/live framework or installed-package suite.

## Implementation plan

### 1. Complete existing defaults

Add `plaintext` and `value` to packaged defaults and add `plaintext`, `value`, and `encryptionkey` to the hardcoded/browser fallback where absent. Verify `secret`, `clientSecret`, mixed-case fields, nested arrays/objects and input immutability. Preserve `mergeWithHardcodedDefaults`, `neverMaskFields`, substring matching and custom-path behavior.

Additional implementation best-practices to apply:

- Change only the existing token lists; reuse normalized comparison rather than adding aliases or branches.
- Treat generic `value` masking as an intentional observable logging change and document it.

### 2. Exclude security bodies at log construction

Use the shared pathname predicate before request/response bodies enter production or test debug contexts. Omit both bodies or use one constant placeholder. Apply it on success and failure, independently of permissive custom masking. Keep sizes and other safe metadata unless a test proves a size itself violates the agreed contract.

Additional implementation best-practices to apply:

- Parse pathname once and test segment boundaries; never use a raw substring match across the full URL.
- Pass guarded bodies into existing formatters without mutating request metadata, outgoing data or returned responses.
- Preserve current sanitizer and fallback logging; do not add raw exception/config dumps.

### 3. Add focused regression proof

Extend existing masker/loader tests and add `tests/unit/security-http-logging.test.ts` only if that keeps transport cases clearer. Exercise the real production logging path under a scoped non-test `NODE_ENV`, restore global state, and drain deferred tasks. Add one parity assertion for the test-only branch and extend the existing loopback fixture rather than adding a framework.

Additional implementation best-practices to apply:

- Capture complete final records, assert a safe event exists, then scan serialized messages and context for every unique marker.
- Parameterize distinct routes/paths without creating a Cartesian product.
- Keep event mode disabled in one ordinary loopback delivery assertion to cover the separate HTTP serialization path.

### 4. Update docs and validation evidence

Update `docs/audit-and-logging.md`, update `docs/encryption.md` only if it contradicts the behavior, and add a concise Unreleased changelog note. Record focused, gate, E2E, package and live/blocked evidence in this plan and `.temp/validation/` without raw secrets or records.

Additional implementation best-practices to apply:

- Document behavior and compatibility, not internal implementation narration.
- Persist only safe counts, booleans, correlation IDs and cleanup status from live capture.
