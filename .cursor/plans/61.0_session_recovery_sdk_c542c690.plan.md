# 61.0 — Miso-Client Session Recovery Controls

## Goal
Introduce explicit browser DataClient controls for activity-driven session refresh so app-level orchestrators can disable SDK activity listeners when needed, while preserving request-driven 401 recovery (`onSessionRestore` / `onTokenRefresh`) behavior.

## Source Alignment (from dataplane plan 441.0)
- This plan is the SDK extraction of the `aifabrix-miso-client` scope defined in:
  - [`/workspace/aifabrix-dataplane/.cursor/plans/441.0_session_recovery_unification_797fd5b4.plan.md`](/workspace/aifabrix-dataplane/.cursor/plans/441.0_session_recovery_unification_797fd5b4.plan.md)
- It is expanded to serve as a handoff specification for creating a parallel plan in:
  - `aifabrix-miso-client-python`

## Scope
- In scope:
  - Add DataClient config options to control activity listener enablement and interval.
  - Gate activity-listener registration in SDK core by the new config.
  - Keep 401 recovery flow behavior unchanged.
  - Add/adjust unit tests for toggle behavior and recovery regression protection.
  - Update SDK documentation and changelog for the new configuration.
- Out of scope:
  - Changes in dataplane/miso repositories.
  - Controller API contract/schema changes.
  - Python SDK implementation changes (this plan provides handoff details only).

## Canonical Repo
- [`/workspace/aifabrix-miso-client`](/workspace/aifabrix-miso-client)

## Baseline (verified before implementation)
- Current browser activity listener registration is wired in `DataClientCore` constructor and uses fixed `60000ms`.
- Current activity events: `mousemove`, `click`, `keydown`.
- Current 401 recovery is request-driven and restore-first by default:
  - `onSessionRestore` when `preferCookieSessionRestore !== false`;
  - then `onTokenRefresh` when restore path does not return a usable session;
  - successful result is persisted via shared browser session persistence.

## Contract Delta Specification (TypeScript SDK)

### 1) Public config contract changes (`DataClientConfig`)
- File: [`/workspace/aifabrix-miso-client/src/types/data-client.types.ts`](/workspace/aifabrix-miso-client/src/types/data-client.types.ts)
- Add fields:
  - `enableActivitySessionRefresh?: boolean`
    - Contract meaning: turns browser activity-driven refresh listener on/off.
    - Policy requirement: this value must be explicitly provided; no implicit behavior is accepted.
  - `activitySessionRefreshIntervalMs?: number`
    - Contract meaning: interval for activity-based refresh checks.
    - Policy requirement: this value must be explicitly provided.
    - Validation requirement: invalid values (`<=0`, `NaN`, non-finite) normalize to policy default.

#### Old -> New (quick contract map)
| Area | Old | New | Compatibility expectation |
| --- | --- | --- | --- |
| Activity listener toggle | Implicitly enabled when browser + `onTokenRefresh` | `enableActivitySessionRefresh?: boolean` | Coordinated consumers must set explicit value; no implicit behavior is accepted |
| Activity interval | Fixed internal `60000` | `activitySessionRefreshIntervalMs?: number` | Coordinated consumers must set explicit interval policy |

### 1.1) Public export contract checks
- `DataClientConfig` remains publicly exported via `sdk-exports`.
- No rename/removal of existing public symbols related to session callbacks:
  - `UserSessionTokenResult`
  - `DataClientConfig`
  - `DataClient`
- Any additive field must follow coordinated-rollout policy and be documented as explicitly configured by consumers.

### 1.2) Server-provided config contract boundary (`DataClientConfigResponse`)
- This plan does **not** require changing `DataClientConfigResponse` or client-token endpoint payload shape.
- `autoInitializeDataClient` behavior remains unchanged unless explicitly expanded in a separate plan.
- If implementation decides to extend server-provided config in this plan, that must be treated as a separate contract delta and documented explicitly before coding.

### 2) Runtime wiring contract changes
- File: [`/workspace/aifabrix-miso-client/src/utils/data-client-core.ts`](/workspace/aifabrix-miso-client/src/utils/data-client-core.ts)
- Enforcement precondition:
  - SDK fails fast whenever either `enableActivitySessionRefresh` or `activitySessionRefreshIntervalMs` is not explicitly provided.
  - No mode-selection branching is allowed for this SDK version.
- Required runtime behavior:
  - Before: listener setup happens whenever browser + `onTokenRefresh`.
  - After: listener setup happens only when browser + `onTokenRefresh` + `enableActivitySessionRefresh !== false`.
- Interval resolution:
  - Before: fixed `60000`.
  - After: resolved from `activitySessionRefreshIntervalMs` with deterministic normalization for invalid values.

### 3) Internal helper constraints
- File: [`/workspace/aifabrix-miso-client/src/utils/data-client-activity-refresh.ts`](/workspace/aifabrix-miso-client/src/utils/data-client-activity-refresh.ts)
- Keep existing callback/teardown contract stable:
  - `setupActivityDrivenRefreshListener(...) => (() => void) | null`
  - `registerRefreshCallback("browser", ...)` paired with `unregisterRefreshCallback("browser")`
- No required changes to event set (`mousemove`, `click`, `keydown`) unless implementation evidence requires it.

## Explicit No-Change Contracts
- `UserSessionTokenResult` public shape is unchanged:
  - `token: string`
  - `expiresIn?: number`
  - `expiresAt?: string`
- Callback signatures remain unchanged:
  - `onSessionRestore?: () => Promise<UserSessionTokenResult | null>`
  - `onTokenRefresh?: () => Promise<UserSessionTokenResult | null>`
- Restore-first semantics remain unchanged:
  - `preferCookieSessionRestore` still controls restore-before-refresh behavior.
- No controller endpoint contract changes (`session`/`refresh`/`logout`).
- No header/auth scheme changes.

## Implementation Plan
1. Extend `DataClientConfig` with activity-refresh controls and define normalization/default behavior.
2. Update DataClient initialization to gate listener wiring based on `enableActivitySessionRefresh`.
3. Resolve runtime interval from `activitySessionRefreshIntervalMs` with deterministic invalid-value normalization semantics.
4. Keep request-driven 401 session restore/token refresh hooks behaviorally equivalent.
5. Add regression-focused unit tests:
   - listener disabled: no activity-based background refresh registration;
   - listener enabled: configured interval behavior remains bounded/expected;
   - invalid interval values normalize to safe default;
   - 401 recovery path still triggers restore/refresh + retry semantics.
6. Update docs/changelog with option names, defaults, browser-only notes, and orchestration ownership guidance.

## Rollout Enforcement Notes
- Activity-listener policy must be explicitly set (`enableActivitySessionRefresh` and `activitySessionRefreshIntervalMs`).
- SDK fails fast whenever explicit activity policy is missing.
- Implicit listener behavior is not accepted as valid state.
- Request-driven 401 recovery callbacks remain mandatory while activity listener policy is enforced.
- This plan must not change restore-first ordering or silently alter 401 retry semantics.

## Expected Automated Tests
- Unit: missing explicit activity policy (`enableActivitySessionRefresh` or `activitySessionRefreshIntervalMs`) throws configuration error (fail-fast).
- Unit: activity listener is not registered when disabled.
- Unit: activity listener uses configured interval when enabled.
- Unit: invalid/zero/negative interval falls back to safe default behavior.
- Unit: listener-disabled init path does not leave refresh-callback registration side effects.
- Unit: 401 recovery remains functional when activity listener is disabled.
- Unit: restore-first behavior (`preferCookieSessionRestore`) is unaffected by activity-toggle settings.
- Integration: listener disabled policy => no background activity-refresh listener registration, while request-driven 401 restore/refresh still succeeds.

All tests in this section are repository-local and executable in `miso-client` CI gates only.
