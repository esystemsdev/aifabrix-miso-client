# 67.0 — Browser session lifecycle orchestration

## Product intent

An authenticated browser should remain usable while the user is active, including
when the access JWT is shorter than the browser session. Consumers should not need
independent network-recovery timers, cooldowns or 401 recovery helpers. Application
idle/logout policy remains consumer-owned.

This plan replaces the rejected session approach previously described as plan 66:
the SDK, not each UI, owns coordination. It addresses the gaps exposed by
`aifabrix-miso#254` and the follow-up review; it does not claim the earlier plan
solved that incident.

## Historical incident and original fix

Keep this section as durable context for future session-TTL investigations.

Source: [Miso issue #254 — Keep open authenticated pages usable past the short
access JWT](https://github.com/esystemsdev/aifabrix-miso/issues/254). The issue was
implemented in Miso plan 237.0 and commit
`5b532ec3dc67159adc58bff617193b9504588ff7` on 2026-09-22.

### Problem that was reproduced

- The Keycloak access JWT intentionally lived for about 300 seconds while the
  browser/user-idle session lived for 30 minutes.
- A logged-in AppShell page such as Dashboard or Evidence Kinds could remain visible
  without mouse or keyboard input. Dashboard status polled every five seconds.
- When the HttpOnly `miso_access_token` expired, protected polling changed from 200
  to 401 and the permission refresh also returned 401.
- The shell still displayed the signed-in user because its 30-minute idle timer had
  not expired, while page content showed **Permissions unavailable**.
- The existing DataClient activity refresh did not cover this topology because an
  open page with polling but no user input produced no activity event.
- The controller already supported `GET /api/v1/auth/session`, which could reuse or
  rotate the cookie-backed session; the open AppShell simply did not call it.

### Original frontend-only fix

The first fix deliberately kept the short JWT and 30-minute idle policy unchanged:

| Component | Original change |
| --- | --- |
| `browser-session-keepalive.ts` | Wrapped `restoreBrowserSession()` / `GET /api/v1/auth/session`; added module-local single-flight and a 60-second cooldown; skipped login/logout/callback paths |
| `useAuthenticatedSessionKeepAlive.ts` | Mounted in `AppShell`, touched immediately and every 240,000 ms; disabled for dev auth bypass |
| `controller-http-session-retry.ts` | On a non-auth-path 401, touched the session and retried the original request once; never retried 403 |
| Tests/docs | Added hook, keepalive and request-retry tests and documented JWT versus idle TTL |

It did **not** change Keycloak `accessTokenLifespan`,
`AUTH_BROWSER_SESSION_TTL_SECONDS`, controller routes/OpenAPI/RBAC, the existing
`AuthIdleSessionWindow`, Tenant Activation's separate pause behavior, or
DataClient's mouse/keyboard activity refresh.

The recorded validation was a 12-minute open-page pass and a roughly 30-minute
idle redirect to `/login`. That evidence showed the visible regression was fixed
without lengthening the JWT. It did not prove server-side session invalidation at
idle, multi-tab coordination, production rate-limit headroom, background-timer
behavior, or that a cooldown-suppressed 401 performed a real restore. Those remaining
questions are why this SDK plan exists.

## Scope

### In scope

- A framework-neutral recovery coordinator inside `DataClient` for periodic,
  visibility, online, explicit and unauthorized triggers.
- One in-process single-flight and one in-memory periodic schedule per active
  DataClient. Consumers support exactly one active authenticated DataClient/tab.
- An unauthorized trigger that is never suppressed by recent successful scheduled
  recovery but never bypasses single-flight/failure backoff; consumers may retry the
  failed request at most once.
- Periodic short-token recovery while the application keeps DataClient alive.
- Preserve the original four-minute (`240000` ms) default periodic cadence. Legacy
  activity-triggered network recovery and its one-minute cooldown are removed;
  consumer-owned activity may still reset an application idle deadline but creates
  no SDK auth request.
- Server-authoritative lifecycle replacement: a disposed DataClient is never revived
  in place. A new client starts a new in-memory schedule without bootstrap recovery;
  explicit/manual and 401 recovery remain available.
- A clean replacement public configuration with no backward-compatibility
  requirement, plus lifecycle teardown, documentation, a semver-major release and
  mandatory Miso/Dataplane migration examples.

### Out of scope

- Miso controller endpoints, cookie format, server-side idle storage or rate-limit
  policy.
- React hooks, UI redirects and application-specific permission reloads.
- Retrying arbitrary HTTP methods or more than one request attempt.
- Python SDK parity.
- Compatibility shims, deprecated aliases, dual-mode behavior or runtime support for
  the superseded browser-session configuration.
- SDK ownership of user activity, idle deadlines, server logout, UI cleanup,
  navigation, long-running-operation holds or pause/resume semantics. Existing
  application idle/hold mechanisms remain application-owned.
- Public lifecycle telemetry, adaptive token-buffer changes, new expiry-normalization
  rules, distributed state merging, durable terminal history and any cross-tab
  coordination, leadership, cookie-ordering or continuity guarantee.

## Architecture alignment

The SDK owns network recovery policy. The controller remains the authority for
authentication and server-session expiry. Applications keep their current idle,
logout, navigation and long-operation pause/hold ownership and dispose the DataClient
when recovery must stop. The replacement contract removes only duplicate recovery
configuration; consumers may pin the preceding npm version for rollback.

No parallel session manager or browser-storage protocol is added. Extend the current
DataClient recovery path. Miso and Dataplane document that correctness is guaranteed
for one active authenticated browser tab; an unsupported multi-tab conflict may
require re-authentication but must remain fail-closed.

## Rules and Standards

- [Architecture Patterns](../rules/project-rules.mdc#architecture-patterns): extend
  DataClient's existing lifecycle components rather than adding a parallel client.
- [Token Management](../rules/project-rules.mdc#token-management): browser callbacks
  may transport session results but never expose client credentials.
- [Code Style](../rules/project-rules.mdc#code-style): public interfaces and outputs
  remain typed and camelCase.
- [Testing Conventions](../rules/project-rules.mdc#testing-conventions): Jest tests
  cover success, failure, concurrency and browser-adapter edge paths.
- [Security Guidelines](../rules/project-rules.mdc#security-guidelines): tokens,
  cookies and callback payloads never enter logs, storage messages or telemetry.
- Do not log, persist or broadcast tokens, cookies, claims or callback payloads. The
  scheduler is memory-only and creates no SDK Web Storage record.
- Treat 401 as recoverable once; 403 is authorization and must not trigger renewal.
- Every recovery listener and timer must be removed on
  `dispose()`; consumers await its drain before server logout or client replacement.
- A failed recovery must preserve the existing error taxonomy and may not silently
  report success because another trigger was recently suppressed.
- Public API names remain camelCase. Superseded configuration should fail clearly at
  TypeScript compile time rather than remain accepted through aliases.
- Publish as the next semver-major version. Rollback is version-based: consumers pin
  the preceding npm version and restore its matching lockfile/integration commit.

## Normative public contract (implementation SSOT)

This section is the handoff contract for a fresh implementation agent. Do not invent
a second API during implementation. A different public shape requires updating this
plan, re-running plan validation and obtaining approval before product-code changes.

### Replacement types

Add and export the following concepts from the package root. Exact property names are
normative; implementation-only adapters may add private fields.

```ts
export type BrowserSessionRecoveryTrigger =
  | "periodic"
  | "visibilitychange"
  | "online"
  | "unauthorized"
  | "manual";

export type BrowserSessionRecoveryOutcome =
  | "recovered"
  | "coalesced"
  | "suppressed"
  | "failed";

export type BrowserSessionRecoveryReason =
  | "disabled"
  | "disposed"
  | "failure-backoff"
  | "unauthorized"
  | "network"
  | "rate-limited"
  | "server"
  | "invalid"
  | "unexpected";

export interface BrowserSessionRecoveryResult {
  trigger: BrowserSessionRecoveryTrigger;
  outcome: BrowserSessionRecoveryOutcome;
  attempted: boolean;
  recovered: boolean;
  reason?: BrowserSessionRecoveryReason;
}

export type BrowserSessionCallbackFailureReason =
  | "unauthorized"
  | "network"
  | "rate-limited"
  | "server"
  | "invalid"
  | "unexpected";

export type BrowserSessionRecoveredAuth =
  | { kind: "bearer"; session: UserSessionTokenResult }
  | { kind: "cookie"; expiresIn?: number; expiresAt?: string };

export type BrowserSessionCallbackResult =
  | { ok: true; auth: BrowserSessionRecoveredAuth }
  | {
      ok: false;
      reason: BrowserSessionCallbackFailureReason;
      status?: number;
      retryAfterMs?: number;
    };

export interface BrowserSessionLifecycleConfig {
  restore: () => Promise<BrowserSessionCallbackResult>;
  refresh?: () => Promise<BrowserSessionCallbackResult>;
  clearCachedAuthState?: () => Promise<void> | void;
  periodicRefreshIntervalMs?: number;
}
```

Retain the package's existing exported `UserSessionTokenResult` shape unchanged.
For `auth.kind: "bearer"`, the real recovered bearer flows through the current
DataClient persistence path before recovery is reported successful or a request is
replayed. For `auth.kind: "cookie"`, successful callback completion is usable
recovery but DataClient persists no token, invents no sentinel and injects no
SDK-managed user `Authorization` header; replay preserves the consumer's credentialed
cookie transport. The SDK must not expose or request an HttpOnly JWT. Neither mode
authorizes new expiry-normalization behavior.

`DataClientConfig` receives one optional
`browserSession?: BrowserSessionLifecycleConfig`. When it is absent, DataClient
installs no browser-session recovery listeners or timers. When present, `restore` is
required.
`periodicRefreshIntervalMs` defaults to `240000` and must be a finite positive integer.
The 30000 ms failed-unauthorized backoff is intentionally not configurable in this
major. The supported one-tab bound of four scheduled recoveries/eight actual auth HTTP
requests per rolling 15 minutes applies only to the default interval. Consumers
choosing a shorter interval own its rate impact.

`clearCachedAuthState` is an auth-cache callback only. It must not remove unrelated
application storage. The SDK creates no browser-storage coordination record.

For callback failures, `status` is accepted only as an integer from 400 through 599;
`retryAfterMs` is accepted only for `rate-limited`. Expected HTTP/network failures
must be returned in the discriminated result, not thrown. The SDK treats a thrown
value, contradictory fields or an invalid success payload as `unexpected`/`invalid`
according to the recovery rules below.

The success discriminator is mandatory and is not compatibility decoration. A
cookie-mode callback may return only non-secret expiry metadata after its credentialed
HTTP response has completed. It must never return a placeholder such as
`__cookie_session_authenticated__`. An invalid/missing discriminator or a bearer
success without a valid `UserSessionTokenResult` is classified as `invalid`.

Remove these superseded top-level `DataClientConfig` properties in the major release:
`onTokenRefresh`, `onSessionRestore`, `clearCachedBrowserAuthState`,
`preferCookieSessionRestore`, `enableActivitySessionRefresh` and
`activitySessionRefreshIntervalMs`. Do not retain aliases, overloads or runtime
translation. Update every SDK test fixture and sample to the replacement object.

Add public instance methods:

```ts
recoverBrowserSession(
  trigger: "unauthorized" | "manual",
): Promise<BrowserSessionRecoveryResult>;
recordBrowserSessionReplayUnauthorized(): void;
dispose(): Promise<void>;
```

`recordBrowserSessionReplayUnauthorized()` is the narrow feedback hook for a raw
consumer request that performed real unauthorized recovery, replayed one eligible
GET/HEAD, and received 401 again. It performs no I/O, changes no periodic
state and only arms the coordinator's existing per-DataClient 30000 ms
failed-unauthorized backoff. SDK-managed requests invoke the same internal transition
automatically. Calling it after disposal is a no-op. It is not a general response,
telemetry or cooldown API.

`dispose()` is asynchronous and idempotent. Before its first suspension it marks the
instance disposed/quiescing, stops recovery, removes every timer, visibility/online
listener, and prevents new periodic/catch-up/manual/401
recovery I/O. It then drains the one current in-process recovery callback, if any,
before resolving. Concurrent dispose callers receive the same drain promise.

Once quiescence starts, completion of the drained callback cannot start refresh
fallback, persist recovered auth state, schedule a request replay or mutate recovery
state. Existing owner/coalesced recovery promises settle as non-recovered/disposed;
the drain itself resolves after success or failure and does not reject because the
recovery callback failed. Calling recovery after disposal returns a non-recovered
result without starting I/O. Consumers must `await dataClient.dispose()` before a
server logout, authenticated-client replacement or reset-to-auth-flow operation.
DataClient request handling uses the same internal recovery entry point; it must not
retain the separate `data-client-auth-recovery.ts` single-flight state.

The drain guarantee requires every supported user browser-session recovery path in a
consumer to enter through this DataClient coordinator. Consumer hooks may retain idle
pause/resume or other application state, but must remove direct restore/refresh calls
and independent network keepalive timers. If a demonstrated workflow still needs an
explicit touch, it delegates to `recoverBrowserSession("manual")` so single-flight and
disposal cover it; it never invokes the transport callback directly.

There is no public restart/reinitialize API. A disposed instance is replaced by a new
`DataClient`. Construction starts its first in-memory deadline at
`now + periodicRefreshIntervalMs` and performs no bootstrap restore. Explicit/manual
and 401 recovery remain available.
When `browserSession` is absent, `recoverBrowserSession()` returns
`{ trigger, outcome: "suppressed", attempted: false, recovered: false,
reason: "disabled" }`; after disposal it returns the same shape with
`reason: "disposed"`. `dispose()` is a local recovery barrier only: it does not clear
auth state, call logout, implement idle policy or alter application-owned
long-operation holds.

The consumer ordering is normative: begin/await SDK disposal first, then perform
server logout, then clear local auth state and navigate even if logout transport
fails. “Server-first logout” means before local auth cleanup/navigation, not before
SDK quiescence. The local drain ensures an already-running recovery settles before the
consumer issues logout, so the logout request uses the browser's current cookie.
For the supported one-tab topology, no SDK recovery callback remains able to commit
after disposal resolves and logout begins. The existing controller logout remains
responsible for ending the server session and clearing the existing cookie. Ordinary
401 responses must not clear the named cookie because a late failed request could
erase a newer cookie installed by the drained recovery. This plan provides no
arbitrary concurrent or multi-tab recovery-versus-logout guarantee and requires no
controller CAS/store/Redis protocol.

### Recovery behavior

- Periodic recovery is an unconditional cookie-session `restore()` every configured
  `periodicRefreshIntervalMs` (240000 ms by default) while DataClient remains alive
  and is scheduled in memory by that DataClient. Construction performs no immediate
  restore. When overdue it performs at most one catch-up, advances the in-memory
  deadline to the first future anchor-relative time and does not replay missed ticks.
- `visibilitychange` to visible and `online` perform no independent network recovery.
  They only wake the instance scheduler and perform at most one catch-up when its
  in-memory deadline is overdue. Token `expired/due` state alone never creates an
  automatic visibility/online request.
- `unauthorized` is not suppressed by a recent successful periodic/catch-up recovery,
  but never bypasses in-instance single-flight, disposal, HTTP 429 suppression or the
  30-second failed-unauthorized backoff. Concurrent 401s in one DataClient join the same
  operation. Independent 401s during backoff receive a suppressed result and preserve
  their original 401.
- `manual` obeys disposal, 429 suppression, failure backoff and single-flight.
- Recovery order is cookie-first `restore()`, then optional `refresh()` only for a
  typed `unauthorized` or `invalid` restore failure. Call
  `clearCachedAuthState()` before that one fallback. `network`, `rate-limited`,
  `server` and `unexpected` failures stop immediately without fallback. A thrown
  callback is normalized to `unexpected`; callback adapters are required to return
  typed failures for expected conditions. A malformed `ok: true` result is
  normalized to `invalid`.
- HTTP 429 always produces `rate-limited`, performs no fallback and suppresses new
  recovery in that DataClient until a finite positive `retryAfterMs`, capped at
  900000 ms, expires; when missing or malformed, use the fixed 30000 ms failure
  backoff. It is never retried automatically inside the same recovery operation.
- An SDK-managed `GET` or `HEAD` retries once only after a 401 recovery result with
  `recovered === true`. It never calls recovery for 403 and never retries more than
  once. `POST`, `PUT`, `PATCH` and `DELETE` may perform recovery after 401 for future
  requests but are never automatically replayed and return the original 401. If
  recovery fails/suppresses, preserve the original 401. If recovery succeeds and an
  eligible replay runs, the replay response/error is final: replayed 401 cannot
  recover again and arms the existing 30-second failed-unauthorized backoff for later
  independent 401s; replayed 403 is returned as authorization failure. Raw-fetch
  consumers must call `recordBrowserSessionReplayUnauthorized()` for the same
  transition after their one replay returns 401.
- In-process coalesced waiters receive their own trigger with
  `outcome: "coalesced"`, `attempted: false` and `recovered` copied from the owner
  result. On owner failure they also receive `recovered: false` and its normalized
  reason. The owner receives `attempted: true` with `outcome: "recovered"` or
  `"failed"`. Coalescing is intentionally in-process only.
- Trigger/state precedence is normative:

  | Trigger | Recent successful recovery within one periodic interval | 30-second failed-unauthorized backoff | 429 suppression | In flight | Periodic scheduling |
  | --- | --- | --- | --- | --- | --- |
  | `periodic` | run when its in-memory deadline is due | run | suppress as `rate-limited` | join/coalesce | A due attempt or suppression advances to the next anchor-relative deadline; no burst |
  | `visibilitychange` / `online` | zero HTTP unless the instance deadline is overdue | suppress as `failure-backoff` | suppress as `rate-limited` | wake/join instance | one overdue catch-up advances to the next anchor-relative deadline |
  | `unauthorized` | run | suppress as `failure-backoff` | suppress as `rate-limited` | join/coalesce | does not move the periodic anchor |
  | `manual` | run | suppress as `failure-backoff` | suppress as `rate-limited` | join/coalesce | does not move the periodic anchor |

  Disabled and disposed checks precede the table and return their exact suppressed
  reasons without I/O. The fixed 30-second backoff begins when an operation with an
  unauthorized owner or waiter finishes with any non-rate-limited failure, or when a
  nominally successful unauthorized recovery is followed by a replayed 401.
  Successful recovery clears a previous backoff before replay evaluation; an accepted
  replay leaves it clear. A 429 uses only its own suppression deadline. There is no
  other automatic visibility/online token-due path.
- Successful callbacks retain the package's existing token/cookie persistence
  semantics. General expiry normalization and adaptive refresh-buffer changes are not
  part of this plan. Consumers remain responsible for idle logout, local cleanup,
  navigation and any long-running-operation pause/hold behavior.

### Single-tab schedule and request bound

The supported topology is one active authenticated browser tab with one live
DataClient. Its schedule is memory-only: construction records the first deadline at
`now + periodicRefreshIntervalMs`, periodic completion advances to the first future
anchor-relative deadline, and visibility/online may wake exactly one overdue catch-up.
No Local Storage, Session Storage, BroadcastChannel, leader id, lease, scope or shared
deadline is created.

At the default cadence, one continuously active DataClient performs at most four
scheduled recoveries in any rolling 15-minute window. Each recovery invokes one
`restore()` and at most one permitted `refresh()` fallback, so the scheduled maximum
is eight actual auth HTTP requests. Application activity performs zero SDK auth calls.
In-process coalesced waiters perform zero additional calls. Reactive unauthorized and
manual requests are reported separately and remain bounded by single-flight,
30-second failed-unauthorized backoff and 429 suppression.

Consumer replacement must await disposal of the old DataClient before constructing
the next one. Tests prove StrictMode/remount/reinitialization leaves only one live
timer/listener set and performs no bootstrap restore. Multiple tabs are independent,
unsupported clients: the SDK makes no aggregate request-count, continuity, cookie
ordering or coordinated logout guarantee for them. No multi-tab characterization is
required by this plan.

## Expected Automated Tests

- `REG-SDK-01`: no input events; periodic recovery keeps a short session usable for
  at least three token lifetimes; periodic restore is unconditional and application
  activity creates no SDK auth calls. The bearer-mode case starts with an expired
  bearer, returns a real `UserSessionTokenResult`, persists it and replays one
  GET/HEAD with the recovered bearer. The cookie-mode case completes a credentialed
  restore, persists no token or placeholder, injects no SDK-managed user
  `Authorization` header and replays one GET/HEAD with cookies. Both modes report
  recovery only after callback success.
- `REG-SDK-02`: async disposal marks the instance terminal before awaiting, stops
  periodic/catch-up/manual/401 recovery, removes every SDK listener/timer/subscription
  and leaves no browser coordination record. With a deferred restore or refresh already in
  flight, dispose waits for settlement, starts no fallback, persists/replays nothing,
  resolves without propagating callback failure and returns the same promise to
  concurrent callers. No new I/O begins after quiescence starts.
- `REG-SDK-03`: a 401 immediately after a successful periodic/catch-up attempt still
  performs real unauthorized recovery, then permits exactly one retry. Failed or
  suppressed recovery preserves the original 401; successful recovery makes the
  replay's 401/403/network/server result final without a second recovery. For both
  bearer and cookie success, a replayed 401 arms the existing 30-second per-DataClient
  failed-unauthorized backoff: another independent GET during the window preserves
  401 and starts zero restore/refresh requests, while a post-expiry 401 may recover
  again. Prove the same state transition through the raw-fetch feedback method and
  count actual auth endpoint attempts.
- `REG-SDK-04`: 403 and non-auth errors never invoke session recovery; mutation 401
  may recover future state but never automatically replays POST/PUT/PATCH/DELETE.
- `REG-SDK-05`: simultaneous in-process triggers share one callback;
  owner and every waiter assert the exact trigger/outcome/attempted/recovered/reason
  object, including failed-owner propagation.
- `REG-SDK-06`: one active DataClient starts no bootstrap restore, maintains one
  anchor-relative four-minute schedule and stays within four scheduled recoveries/
  eight actual auth HTTP requests per rolling 15 minutes. Visibility/online storms
  before the deadline create zero HTTP; after an overdue deadline they wake at most
  one catch-up without replaying missed intervals. Awaited replacement, reset and
  StrictMode/remount leave exactly one timer/listener set and no overlapping old
  instance.
- `REG-SDK-07`: the SDK creates no Local Storage, Session Storage, BroadcastChannel,
  leader/lease or shared-schedule state and persists no cookie-mode token/sentinel.
  No activity, idle, logout or hold state is coordinated.
- `REG-SDK-08`: the replacement public configuration compiles and works; compile
  fixtures using removed legacy fields fail with the documented migration error.
  Compile/runtime fixtures cover both success variants and reject an absent/invalid
  discriminator, cookie sentinels and bearer success without a valid session.
  Disabled/disposed instances return the exact suppressed result. The default cadence
  is `240000` ms; 429 and 30-second unauthorized backoff are deterministic. Lifecycle callback
  adapters disable hidden transport retries and tests count actual `/auth/session`
  and `/auth/refresh` endpoint attempts against the supported single-tab four/eight
  bound.
