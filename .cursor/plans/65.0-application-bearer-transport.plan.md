**Order:** 205 Phase 1–2 (token claims + dual transport) → implement this plan’s Bearer-default → consumers upgrade → 205 Phase 4–5 / this plan cleanup.

## Scope

### In scope

- Default application-token transport: `Authorization: Bearer <miso-client-token>`.
- Optional legacy mode that still sends `x-client-token` for older controllers.
- Safe dual-header policy: do not send conflicting tokens; prefer single transport per request.
- Updates to interceptors (`internal-http-client`, `http-client`), `auth-strategy`, error classification, and APIs that hard-require `x-client-token`.
- Tests and docs reflecting Bearer-first application auth.
- Consumer handoff notes for Builder / Miso apps that import this SDK.

### Out of scope

- Changing Miso controller YAML, routes, or OpenAPI (plan 205).
- Dataplane Python call-site migration (after 49.0).
- User/OAuth Bearer semantics changes.
- Removing browser URL `x-client-token` query param if still required for login redirect bootstrap (review and document; do not silently break).

## Rules and Standards

- Follow repo project rules for SDK architecture, auth, and quality gates (build → lint → test).
- Do not log token values.
- Keep public API camelCase.
- Prefer extending existing HTTP interceptors over parallel clients.
- Coordinate claim names with 205 (`principalType`, application/environment, `permissions`) without inventing a second token format.

## Before Development

1. Confirm 205 Phase 1–2 contract: controller accepts application token on Bearer and still accepts legacy header in migration mode.
2. Inventory SDK emission sites: `src/utils/internal-http-client.ts`, `http-client.ts`, `auth-strategy.ts`, redirect helpers, auth APIs.
3. Align with 49.0 so TS and Python defaults match.
4. Do not enable “legacy off” as the only mode until 205 Phase 5 criteria are met.

## Architecture alignment

- Owner: Platform SDK (TS) — transport adapter for Miso application principals.
- Controller remains authority for permissions and ABAC; SDK only presents the token and optional legacy header.
- User Bearer and application Bearer share the same header; controller classifies by trusted claims (205).
- Builder and other Node consumers inherit Bearer-default via this package.

## Code reuse scan

- Reuse existing token fetch/cache (`client-token` managers) — change header attachment only.
- Reuse `auth-strategy` patterns; extend rather than fork.
- Reuse existing 401/403 error handling; update transport labels if needed.
- Do not add a second HTTP stack for “new auth”.

## Expected Automated Tests

- Application token attached as `Authorization: Bearer` by default.
- Legacy mode attaches `x-client-token` when explicitly enabled.
- Default mode does not attach both headers with different values.
- Existing user Bearer flows unchanged.
- Client-token fetch still skips interceptor chicken/egg (client id/secret exchange).
- `[EDGE]` Expired/missing application token surfaces current error taxonomy without leaking token material.
- Redirect/URL helpers: document and test remaining `x-client-token` query behavior if retained.
