# 72.0: exported text masker

## Why

Setup's `af-server logs` (Setup plan 050) must mask a capped log window before printing it, and
the product owner decided that the masking comes from the Miso client. The client has no
function for that. `DataMasker.maskSensitiveData` masks the values of sensitive keys in an
object or array; a string comes back unchanged, and the package root does not export it.

## What changes

One new module, `src/masking/text-masker.ts`, exported from the subpath
`@aifabrix/miso-client/masking` (node, import and require, like `./bootstrap`) and from the
package root:

```ts
export interface MaskedText {
  text: string;
  count: number;
}
export function maskSensitiveText(text: string): MaskedText;
```

- Each masked value becomes `***MASKED***`, the token `DataMasker` already uses. `count` is the
  number of values replaced.
- A non-string argument throws `TypeError`. Any string, including an empty one, invalid
  surrogates or a very large window, returns a result and never throws.
- The module imports only the sensitive-fields loader (Node `fs` and `path`). The subpath does
  not load axios, ioredis, jsonwebtoken, jose, zustand or Express.
- Nothing else changes: `DataMasker`, the logger and the sensitive-fields JSON keep their
  behaviour. The new name rules below apply to text only.

## Rules

The rules run in this order. A span already masked is not counted again.

1. **PEM blocks:** from a `-----BEGIN … -----` line to its `-----END … -----` line, whatever
   the type (private key, certificate, encrypted key). A window that starts inside a block (an
   END line with no BEGIN before it) is masked from the start of the text to that END line. A
   BEGIN with no END is masked to the end of the text. Each block counts once.
2. **JWTs:** three base64url segments separated by dots whose first segment starts with
   `eyJ`.
3. **Authorization values:** the value of an `Authorization:` header, whatever its scheme.
   Without the header, `Bearer <token>` and `Basic <token>` are masked only when the token is
   token-shaped (base64 or base64url, 16 characters or more), so prose such as "Basic auth" is
   kept.
4. **URL userinfo:** the `user:pass` in `scheme://user:pass@host` is masked. A user with no
   password is kept.
5. **Sensitive names in text:**
   - Forms: `name=value`, `name: value`, `"name": "value"`, `'name': 'value'`, a JSON number or
     literal (`"user_pin": 123456`), and query parameters (`?name=value&…`).
   - A name is sensitive if it matches the sensitive-fields list as `DataMasker` matches it
     (normalized; exact, or containing a listed field of 4 or more characters).
   - It is also sensitive in these cases:
     - `pin`, `otp`, `ssn` or `cvv` is one of the name's tokens, split at `_`, `-`, `.` and
       camelCase boundaries (`user_pin`, `smsOtp`). A longer word that only contains the
       letters, such as `spinner` or `option`, is not.
     - `credential`, `signature` or `key` is one of the name's tokens, including the last one
       (`client_credential`, `x-signature`, `api_key`, `x-api-key`, `privateKey`, `key`).
     - The sensitive-fields list's never-mask names stay unmasked, as in `DataMasker`, except
       `key`, which text masks because a log line has no structure to tell a key name from a
       key value.
     - `code` is the name or its last token (`code`, `auth_code`), and the value is 16
       characters or more, or the name is a query parameter. A short code such as
       `status code: 200` or `error_code=E42` is kept.
   - Where the value ends:
     - a quoted value: at its closing quote;
     - a JSON number or literal: at `,`, `}` or `]`;
     - `name=value` and query parameters: at the first whitespace, `&`, `,` or `;`;
     - an unquoted `name: value`: at the end of the line, so `password: two words` hides both
       words.
   - The name is kept; only the value is masked.
6. **Long unnamed runs:**
   - base64, base64url or hex runs of 32 characters or more that are not part of a longer word;
   - a hex run that is 40 or 64 characters long, which is what a git commit, a SHA-256 digest
     or a full Docker container or image ID looks like, is masked too.
   - This trade-off is deliberate: such an ID or hash in a log line is lost, so that an unnamed
     key of that length never shows. The 12-character short container ID is kept.
   - A UUID with dashes is kept.

The masker is a guard against showing a secret by accident, not a security boundary.

## Tests (first, failing before the code)

- One fixture per rule and per name form in `## Rules`, each with a seeded value that must not
  appear in the output and a count that must match.
- A control for each: an ordinary log line that must come back byte for byte, with a count of 0.
  The controls are a timestamp, a UUID, `status code: 200`, `spinner`, `option=1`, "Basic auth"
  in prose, a never-mask name, a 12-character container ID, and a URL without userinfo.
- `password: two words` hides both words; `"user_pin": 123456` hides the number.
- A combined window with every form from Setup plan 050's gap table finds none of the seeded
  values. Those forms are: a PEM block, a window starting inside one, a bearer token, a JWT,
  `password=`, `"token": "…"`, `Authorization:`, `client_secret`, `access_token`, `x-api-key`,
  `privateKey`, a 6-digit `user_pin`, `https://user:pass@host`, `?access_token=…&code=…` and a
  40-character hex run.
- A mutant check per rule: with that rule disabled, its fixture fails.
- A non-string throws `TypeError`; an empty string returns `{ text: "", count: 0 }`.
- An 8 MB window (2000 lines of 4096 bytes, the Setup cap) is masked in under 2 seconds, with
  no regular-expression backtracking blow-up. The input includes long runs without separators.
- Dependency isolation: requiring the built `dist/masking` in a fresh process loads none of
  axios, ioredis, jsonwebtoken, jose, zustand or express.
- Existing `DataMasker` and logger tests pass unchanged.
