## Scope

### In scope

One Node-only `initSecrets()` API supports local configuration and remote Miso
snapshots. Remote authentication is exclusively Miso client ID + secret → client
token → snapshot. Renew with the latest snapshot's client token. Remove the previous
external identity provider, settings, public options and dependency. Export the
snapshot validator for controller tests. Keep SDK-owned diagnostics secret-free.

### Out of scope

Controller authorization/OpenAPI implementation, Python SDK edits, workload deployment,
publishing and application-owned database/Redis connection factories. These owners
must supply interoperability and rollout evidence; SDK tests do not establish it.

## Shared contract and decisions

Source: [controller 257.0](../../../aifabrix-miso/.cursor/plans/257.0-application-bootstrap-endpoint.plan.md).

- Unset/`local` reuses the existing config loader and dotenv precedence. Remote mode
  is exactly `MISO_AUTH_MODE=client-credentials`; it never loads dotenv. Unknown
  modes reject without provider side effects. Mode belongs in deployment settings.
- Remote input requires `MISO_CONTROLLER_URL`, `MISO_CLIENTID`, `MISO_CLIENTSECRET`.
  The aliases `MISO_CLIENT_ID` / `MISO_CLIENT_SECRET` are supported; a nonempty
  canonical name wins. Credential delivery remains deployment-owned.
- Pin HTTPS origin and virtual-directory root before any request. Reject URL
  userinfo/query/fragment and redirects. Never send credentials to normal endpoints.
- Initial grant: `POST /api/v1/auth/token`, headers `x-client-id`, `x-client-secret`;
  HTTP 201 response `data.token`, `data.expiresIn`, `data.expiresAt`. This is the
  controller-supported initial-grant exception to the ordinary client-token rule.
- Snapshot: `POST /api/v1/auth/bootstrap`, `x-client-token`, body exactly
  `{ "protocolVersion": 1 }`; HTTP 200 envelope `{ "success": true, "data": ... }`.
  No request application/environment selectors. Context is assigned by Miso.
- Closed nine-key data: protocolVersion, issuedAt, context, clientId, clientToken,
  clientTokenExpiresAt, configuration, refreshAfter, expiresAt. Context contains
  installationId/applicationId/environmentId only. No clientSecret in snapshots.
- UTC timestamp grammar accepts whole seconds or exactly three fractional digits;
  maximum clock skew ±30 seconds. Offsets from issuedAt are exactly 120s refresh,
  300s advertised token expiry and 900s snapshot expiry. Schedule at 110–120s;
  token/configuration deadlines are independently 30s early with monotonic protection.
- Maximum decoded response 1 MiB; 256 configuration keys; names match
  `^[A-Z][A-Z0-9_]{0,127}$`; values at most 65536 UTF-8 bytes. Reserved settings are
  MISO_AUTH_MODE, MISO_CONTROLLER_URL, both ID/secret aliases, MISO_AUTH_STRATEGY and
  MISO_CLIENT_TOKEN_URI. Obsolete provider settings have no special meaning.
- Initial grant plus snapshot share a 30s deadline. Each endpoint gets at most three
  attempts, 5s each, with transient network/429/502/503/504 retries only, jitter
  [0,1]/[0,2]s and Retry-After no greater than 10s. Refresh failures have a 30s cooldown.

### Rotation, denial and recovery

After success the runtime passes the latest accepted snapshot token directly to the
refresh transport. It must not recursively ask its own `token()` method for that
credential. Healthy refresh does not read ID/secret again or store them in client config.

Snapshot 401/403, malformed responses and context/clientId changes are terminal.
No automatic credential grant occurs after denial. Explicit shutdown and a new
`initSecrets()` use current deployment credentials; stale process environment may
require restart. Secret rotation does not interrupt an otherwise healthy session.

Once the snapshot token reaches its early deadline or is explicitly rejected as
expired, remote refresh does not send that token or mint a replacement. Existing
secret reads retain their independent deadline. Recovery requires reinitialization.
Controller JWT lifetime can be longer than advertised SDK lifetime; the SDK does not
claim server revocation at its own deadline. Ordinary API calls retain existing typed
session-error recognition and never automatically replay failed operations.

### External dependencies still requiring evidence

Controller code has the two endpoints and matches the successful nine-field producer
shape. Its JWT service uses a 900s lifetime and its middleware now emits typed
invalid/expired-token codes. A fresh registration check on every API authorization
and deployed application revocation proof remain outstanding.
The snapshot OpenAPI currently describes optional authentication despite required
middleware, and the route does not enforce the closed request body. Controller 257.0
owns these corrections and deployed revocation proof. They are not silently patched
by changing the SDK's ordinary user/permission error handling.

Python now matches the eight reserved configuration keys and the whole-second/three-digit
fractional timestamp grammar. Revalidation accepted the same controller-produced fixture
in both SDKs at its issuedAt clock. This single positive fixture is not a complete
cross-SDK boundary/failure corpus; full interoperability and live proof remain open.

## Code reuse and ownership

Reuse Axios and `joinApiRoot`. Do not use ordinary token helpers for bootstrap:
interceptors can recurse and their diagnostic errors retain sensitive inputs.
Keep remote code separate from config-loader/root-barrel dotenv hydration.
`RuntimeState` owns deadlines, snapshots, refresh and guards; deployment owns initial
credentials. SDK-owned connections close within 5s; no claim of erasing caller copies
or cancelling requests already sent. No secret writes to environment, disk or Redis.
