# 69.0 — Forbidden is not session expiry

## Goal

Correct one status-classification defect in `src/utils/data-client-request.ts`.
The current `isAuthStatus()` and `isAuthErrorInstance()` treat both `401` and
`403` as authentication failures. Recovery is already limited to 401, but the
403 branch still reaches `handleAuthErrorCleanup()`, allowing a legitimate RBAC
or Dimension authorization denial to clear authentication and redirect the user
to login.

The required behavior is:

- `401 Unauthorized`: retain plan 67's bounded browser-session recovery,
  replay, and terminal authentication handling.
- `403 Forbidden`: preserve one request and the original typed 403; do not
  recover, refresh, clear cached authentication, or redirect to login. Route it
  through the applicable final failure path and `onError` behavior. Promote it
  to `ApiError` before success parsing or `onResponse`; otherwise the current
  response pipeline can return a 403 as successful interceptor output. An
  initial 403 uses the existing non-retryable failure/audit path. A 403 returned
  by the one allowed post-recovery replay remains immediately final through plan
  67's existing replay-final branch. If no `onError` interceptor intentionally
  transforms it, preserve the original status and `Response` instance.
- Other non-auth statuses such as 404 and 503: retain their existing error
  behavior and never enter session recovery.

## Verified Current State and Exact Gap

| Area | Current behavior | Plan decision |
| --- | --- | --- |
| `handleAuthResponse()` | Recovery itself is already restricted to 401, but the shared 401/403 predicate still sends a terminal 403 through `handleAuthErrorCleanup()` | Make the entry predicate 401-only; do not add another recovery path |
| `shouldPropagateAuthError()` | Marks 403 as an authentication failure and bypasses the ordinary non-retryable handler | Use the same 401-only authentication predicate |
| `handleNonRetryableRequestError()` | Special-cases both 401 and 403 as authentication | Retain the special case only for 401; 403 uses the existing failure/audit path |
| `handleFinalError()` | `isAuthErrorInstance()` suppresses the configured `onError` interceptor for an `ApiError(403)` | Classify only `AuthenticationError`/status 401 as authentication; 403 follows normal interceptor semantics |
| Success processing | `processSuccessfulResponse()` invokes `onResponse` before checking `response.ok`; after a predicate-only fix, `onResponse` could convert 403 into a successful result. Its cache helper already rejects non-OK responses | In the request pipeline, throw `ApiError(403)` immediately after 401 handling and before parsing/success processing; do not reorder the shared response helper or change cache logic |
| Post-recovery replay | `handleAttemptError()` makes every replay result final before generic propagation/non-retryable handling | Preserve this plan 67 branch: replayed 403 skips generic failure/audit orchestration, reaches outer `onError` once, and causes no second recovery/retry or replay-401 reporting |
| `isRetryableError()` | Already makes both 401 and 403 non-retryable | No logic change; 403 must remain non-retryable |
| Existing focused tests | Strong 401 lifecycle coverage exists; the 403 test checks only that recovery is absent | Strengthen that test and add only the interceptor assertion needed to cover the second affected branch |
| Bootstrap transport | Has its own typed 401/403 bootstrap failure contract | No change; it does not use this DataClient terminal-cleanup path |

This is a correction to the completed plan 67 invariant that 403 is
authorization and never enters browser-session recovery or termination. It is
not a new session lifecycle or HTTP error taxonomy.

## Deferred Plan 65 Boundary

Plan `65.0-application-bearer-transport.plan.md` is deliberately deferred and is
not a prerequisite, dependency, or implementation surface for this plan. Plan
69 classifies a DataClient request's final HTTP result (`401` versus `403`) and is
therefore independent of whether a future application credential is transported
in `x-client-token` or `Authorization: Bearer`.

Plan 69 must not change token attachment, application/user token distinction,
auth strategy selection, bootstrap credentials, headers, redirect URL token
parameters, or any public configuration proposed by plan 65. A later plan 65
implementation must preserve the invariant established here: transport choice
does not turn a final authorization denial into session expiry.

## Scope

### In scope

- `src/utils/data-client-request.ts`: replace ambiguous 401/403 authentication
  predicates with 401-only predicates, use them consistently in response,
  thrown-error, non-retryable and final-interceptor classification, and simplify
  authentication-error construction to the only valid status (401). Add one
  narrow status-403 failure guard after authentication handling and before
  response parsing/success processing.
- `tests/unit/data-client-request.test.ts`: strengthen only the focused 403
  regression and reuse the existing 401 tests.
- One Unreleased changelog entry for the corrected observable SDK behavior.

  application-Bearer transport changes.
- Any implementation, partial migration, compatibility flag, documentation, or
  test belonging to deferred plan 65.
- Broad HTTP error taxonomy refactoring or changing bootstrap-specific 403
  classification in `src/bootstrap/transport.ts`.
- Changes to `handleAuthErrorCleanup()`, browser storage, redirect code,
  `isRetryableError()` behavior, public types, or exports.
- Changing the existing `state.tokenRefreshAttempted && attempt > 0` replay-final
  branch or defining new audit behavior for replay errors.
- Reordering `processSuccessfulResponse()` or changing caching/interceptor
  behavior for 400, 404, 5xx, or any status other than 403.
- Retrying 403, converting it to 401, suppressing it, or making authorization
  failures appear successful.

## Expected Automated Tests

- 403 performs exactly one fetch and rejects with the original response/status.
- 403 does not call `recoverBrowserSession`, replay-unauthorized reporting, or
  `handleAuthError` (the existing cached-auth cleanup and login-redirect gateway).
- With `onResponse` and `onError` configured, 403 never enters `onResponse` and
  reaches `onError` exactly once as an `ApiError(403)` that retains the original
  `Response`.
- A GET receiving 401, recovering successfully, and then receiving 403 performs
  exactly two fetches and one recovery; the replayed 403 remains final with its
  replay `Response`, invokes outer `onError` once, and triggers no cleanup,
  replay-401 reporting, second recovery, or retry.
- Existing 401 tests still prove at most one recovery and one safe GET/HEAD
  replay, terminal/replayed-401 handling, and no mutation replay.
