## Proposed Public API Shape
- `formatDateTime(value, options?)` — main formatter for UI display.
- `formatDate(value, options?)` and `formatTime(value, options?)` — optional helpers for common UI cases.
- `createDateTimeFormatter(options?)` — optional factory for repeated rendering paths (tables/lists) to avoid repeated option assembly.

All APIs remain framework-agnostic (no React dependency in SDK).

## Recommended Contract Decisions
- **Input types**: support `string | number | Date | null | undefined` and normalize internally before formatting.
- **No-throw behavior**: formatter functions should never throw on bad input; return `fallback` (default `-`) or original trimmed value per documented rule.
- **Default rendering policy**: when options are omitted, use browser/runtime locale and browser local timezone.
- **Override policy**: allow explicit `locale` and `timeZone` only as opt-in overrides; do not force global locale/timezone state.
- **Invalid-value semantics**: define one consistent behavior for invalid/parsing-failed inputs and keep it identical across `formatDateTime`, `formatDate`, `formatTime`.
- **Deterministic factory behavior**: `createDateTimeFormatter(options?)` must apply the same formatting semantics as one-off formatter calls.

## Recommended Best Practices for Execution
- **Prefer pure, side-effect-free formatters**: keep formatting functions deterministic and independent from global mutable state so they are safe in React render paths and reusable in any UI layer.
- **Centralize parse + guard behavior**: handle `null`/`undefined`/empty strings/placeholders and invalid dates in one utility path to avoid each consumer re-implementing fallback logic differently.
- **Use `Intl.DateTimeFormat` instance reuse for hot paths**: when rendering large tables, rely on `createDateTimeFormatter()` (or equivalent memoized factory) to avoid creating a new formatter per cell.
- **Design options as additive and backward-compatible**: keep defaults stable (browser locale + browser timezone), and only add optional overrides (`locale`, `timeZone`, `dateStyle`, `timeStyle`) to minimize breaking changes for consumers.
- **Test with explicit locale/timezone inputs**: avoid brittle tests tied to CI machine locale; pin locale/timezone in test cases that verify output shape and reserve separate tests for default-runtime behavior.
- **Document UX semantics explicitly**: describe what happens for invalid or missing values (for example fallback `-`) and recommend consumer usage patterns for list rows, details pages, and audit/log timestamps.
- **Include migration examples from existing UI patterns**: in docs, show before/after replacement snippets for `miso-ui` and `dataplane` style usages to speed up adoption and reduce duplicate date helpers.

## Risks and Mitigations
- **Locale output variance across environments**: mitigate with tests that pin explicit locale/timezone and assert stable fragments/shape.
- **Runtime differences (browser vs Node/Jest ICU data)**: mitigate by avoiding exact full-string assertions for default locale tests and adding explicit-locale tests.
- **Inconsistent consumer fallback behavior after rollout**: mitigate with a required migration checklist in the temporary handoff document.
