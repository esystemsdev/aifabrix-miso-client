### Revised behavior and minimal implementation

- Retain `value` in packaged and fallback sensitive-field defaults. Match it as a complete field name, case-insensitively; do not let this token alone mask `totalValue`, `defaultValue`, `values`, `valueCount` or `evaluation`.
- Settled smallest change: preserve existing field-name normalization and exact-match/never-mask precedence; exclude only the normalized sensitive token `value` from the existing substring loop. Because normalization lowercases and removes `_`/`-`, `value`, `VALUE`, `v_a_l_u_e`, `v-a-l-u-e` and any spelling that normalizes exactly to `value` remain masked.
- Other sensitive tokens keep existing matching behavior. A field such as `secretValue` remains masked because `secret` independently matches. Do not introduce an allowlist of benign fields, a new configuration schema/switch, a second masking engine, or a broad matcher refactor.
- Preserve custom configuration semantics: `mergeWithHardcodedDefaults`, `neverMaskFields`, explicit config paths and fallback loading. Universal normalized-token semantics are intentional: `value` is exact-only whether it came from packaged defaults, hardcoded fallback, `fields`, `fieldPatterns`, global config or per-call config. If a custom configuration explicitly lists `totalValue`, it still masks that exact field and retains the existing substring behavior of that non-`value` token. `neverMaskFields` keeps normalized exact precedence.
- Cross-SDK parity is limited to exact-only `value` semantics for token sources that already reach each SDK's matcher. TypeScript already consumes `fieldPatterns`, so a TypeScript `fieldPatterns: ["value"]` token is exact-only; Python currently does not consume `fieldPatterns`, and enabling it is explicitly outside this correction. No config-loading or cross-SDK feature-parity change is planned.
- Compatibility decision: benign composites previously masked solely because they contained `value` become visible in nonsecurity diagnostics. If a composite field actually contains a secret, consumers must configure that field explicitly or use another independently matching sensitive token. Security-route body omission remains the non-configurable boundary.
- Preserve unconditional request/response body omission for `/api/security/*`, fixed safe failure diagnostics, useful safe metadata, and caller/wire data. Do not modify the separate error-type issue or unrelated E2E behavior.
