# 66.0 — Browser session activity renewal hardening

## Problem

`DataClient` already contains browser activity session recovery, but downstream
consumers can still drift into app-owned listeners because important behavior is
implicit or incomplete at the integration boundary. The Dataplane investigation
found dual ownership, cookie-sentinel handling differences, callback results
that may contain only `expiresIn`, and insufficient real-consumer diagnostics.

Miso currently demonstrates the intended separation: its idle window only
enforces local inactivity, while DataClient owns network renewal. The SDK must
make that pattern complete, observable, and safe for all consumers so apps do
not need parallel browser-event orchestration.

## Goal

Make `@aifabrix/miso-client` the robust, framework-agnostic SSOT for non-manual
browser session renewal across Miso, Dataplane, and future browser consumers,
without adding mandatory configuration or changing existing auth endpoints.

## Scope

### In scope

- Define and enforce SDK ownership of activity, visibility, and online recovery.
- Review and harden the default activity signal set for pointer, mouse,
  keyboard, scrolling, and touch-capable browser use without event storms.
- Normalize session callback expiry from `expiresAt`, `expiresIn`, or compatible
  token metadata before storing SDK runtime state.
- Preserve immediate-first behavior, bounded cadence, post-recovery dedupe, and
  single-flight recovery across browser and request-driven paths.
- Provide opt-in, token-safe telemetry for recovery decisions and outcomes.
- Add lifecycle-safe setup/teardown tests and cookie-only integration tests.
- Document exact single-owner consumer wiring for Miso and Dataplane, including
  auth-shell gating and rollback.
- Publish a new package version and changelog entry after validation.

### Out of scope

- Implementing the Dataplane consumer refactor; that is plan
  `577.0-sdk-owned-browser-session-renewal` in the Dataplane repository.
- Changing controller or Keycloak TTLs, cookie attributes, auth endpoints, or
  response wire schemas.
- Owning application idle logout, UI state, route redirects, or manual refresh
  controls inside the SDK.
- Cross-tab global coordination through a new server or browser persistence
  protocol; per-tab bounded behavior and shared-cookie compatibility are in
  scope, but a new distributed lock is not.
- Persisting browser access or refresh tokens as part of the hardening.
- Changes to `miso-client-python`.

## Architecture alignment

- **SDK owner:** browser signal collection, eligibility, expiry scheduling,
  cooldown, dedupe, single-flight, callback invocation, and recovery telemetry.
- **Consumer owner:** local idle policy, UI/auth phase transitions, auth-shell
  route gating, manual recovery, and application request retry presentation.
- **Controller owner:** validating cookie-backed browser state and sliding the
  server-side session on successful session/refresh calls.
- **Compatibility:** retain `enableActivitySessionRefresh`,
  `activitySessionRefreshIntervalMs`, `onSessionRestore`, and `onTokenRefresh`;
  new diagnostics or event policy options must be optional and default-safe.
- **No React dependency:** implementation remains under SDK utilities and uses
  injected/browser interfaces in tests.
- **Rollout:** SDK tests and package → Miso smoke test → Dataplane consumer plan
  and soak. Existing consumers can disable SDK activity with
  `enableActivitySessionRefresh: false` only when they intentionally own an
  alternative path during rollback.

## Code reuse scan

| Need | Reuse | Do not |
| --- | --- | --- |
| Recovery state machine | `createSessionRecoveryOrchestrator` | Create separate state machines per event type |
| Browser listeners | `setupSessionRecoveryOrchestrationListener` and injected browser/document targets | Introduce framework-specific hooks |
| Token freshness | `UserTokenRefreshManager`, `normalizeExpiresAt`, and browser-session expiry helpers | Decode cookie sentinels as JWTs or ignore `expiresIn` |

| Diagnostics | Existing telemetry reasons `cooldown`, `dedupe`, `inflight`, `success`, `failure` | Log tokens, cookies, headers, or callback payloads |
| Consumer examples | Existing DataClient auth/session docs and Miso wiring | Copy consumer UI state into SDK documentation as required code |

## Implementation plan

### Freeze the public renewal contract

Additional implementation best-practices to apply:

- Specify one owner for non-manual recovery and distinguish SDK behavior from
  consumer idle/logout and manual actions.
- Preserve existing configuration keys and callback signatures; any telemetry
  or event-policy extension must be optional.
- Define successful renewal as both server callback success and correctly
  advanced SDK runtime expiry state.

### Harden browser signal orchestration

Additional implementation best-practices to apply:

- Normalize overlapping pointer/mouse/touch/click signals before the shared
  cadence guard so one physical action cannot create a recovery burst.
- Keep visibility and online triggers in the same orchestrator and single-flight
  domain as user activity.
- Expose deterministic teardown suitable for SPA lifecycle tests without
  requiring a React/Vue/Angular adapter.

### Normalize expiry and callback outcomes

Additional implementation best-practices to apply:

- Derive a canonical absolute expiry from a valid `expiresAt`, otherwise from a
  finite positive `expiresIn`, while preserving safe token metadata fallback.
- Advance or clear stale runtime expiry deterministically after a successful
  sentinel-token refresh; never retain an already-expired timestamp silently.
- Treat malformed or failed callback results as bounded failures with no token
  persistence and no immediate retry loop.

### Add safe observability and compatibility tests

Additional implementation best-practices to apply:

- Emit only trigger/reason/timestamp and bounded non-sensitive detail through an
  opt-in callback; do not add unconditional console logging.
- Test the public DataClient boundary with injected browser targets and cookie
  sentinel results, not only isolated helper functions.
- Prove old configurations behave identically when optional additions are not
  supplied.

### Publish consumer guidance

Additional implementation best-practices to apply:

- Provide exact Miso and Dataplane single-owner snippets plus an explicit
  anti-pattern showing dual listeners are forbidden.
- Document supported signals, cadence semantics, expiry precedence, auth-shell
  gating responsibility, telemetry, package version, and rollback.
- Keep changelog wording consumer-facing and free of environment-specific data.

## Manual testing

- **Miso reference:** run the Miso UI with an accelerated development-only
  browser-session idle timeout and prove active versus truly idle controls.
- **Dataplane handoff fixture:** exercise a minimal DataClient browser harness
  using Dataplane callback shapes, including `expiresIn` without `expiresAt`.
- **Signals:** mouse, pointer/touch-capable event, keyboard, scrolling signal,
  visibility return, and reconnect; record which signals are contractually
  supported after implementation.
- **Cadence:** a rapid event burst must produce at most one eligible backend
  recovery within the configured interval.
- **Artifacts:** sanitized telemetry reasons, request counts/statuses, package
  version, and before/test/after TTL values under
  `.temp/plan-validation/evidence/66.0/`; never capture tokens or cookies.
- **Cleanup:** restore temporary TTL settings and close test browser contexts.

- Keep each callback adapter and event handler below 50 lines and avoid a new
  generic utility file that merely relocates oversized logic.
