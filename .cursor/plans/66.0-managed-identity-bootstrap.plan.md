# 66.0 - Managed identity bootstrap (TypeScript)

## Scope

### In scope

Add an opt-in server-side bootstrap entrypoint for Mori and Builder API.
In Azure mode the application supplies only the non-secret Miso URL, expected Entra
audience and optional managed-identity selection. Application context comes exclusively
from Miso. It obtains its approved application token and runtime secrets through Miso
before constructing the SDK or secret-dependent clients.
No Key Vault SDK, role, secret URL or direct vault read is used by the workload.
Managed-app Miso and Keycloak keep their independent platform startup mechanism.
Workload placement in another RG is supported by registered identity, not RG trust.

### Out of scope

Controller verification, registration or vault implementation; consumer application
code; customer apps; browser secret delivery; arbitrary cross-tenant federation;
normal application/user token transport migration; publishing or deployment.

## Shared contract and dependencies

Authority: [Miso 227.4](../../../aifabrix-miso/.cursor/plans/227.4-installation-keyvault.plan.md).
Parity: [50.0](../../../aifabrix-miso-client-python/.cursor/plans/50.0-managed-identity-bootstrap.plan.md).

Deployment supplies these non-secret settings:

```dotenv
MISO_AUTH_MODE=azure-managed-identity
MISO_CONTROLLER_URL=https://<installation-miso-host>
MISO_BOOTSTRAP_AUDIENCE=api://<miso-api-application-id>
```

No MISO_CLIENT_ID/MISO_CLIENTID, client secret or application/environment selector is
required. Prefer system-assigned identity; optional AZURE_CLIENT_ID selects an assigned
Azure identity, not a Miso context. Azure mode requires URL/audience with no guessed
public endpoint or developer-credential fallback. Unknown auth mode fails. Absent mode
or `local` uses the existing local `.env` flow through the same helper; it does not
auto-detect Azure.
MISO_AUTH_MODE is independent of the normal request MISO_AUTH_STRATEGY setting.

POST /api/v1/auth/bootstrap with Entra Authorization Bearer and body
`{ "protocolVersion": 1 }` only. Obtain the Entra token with the configured audience's
`/.default` scope through the official Azure Identity managed-identity implementation;
provide an injectable async token-provider seam for tests. No application context,
client ID, tenant override, vault URI or requested secret list is sent. Token audience
selection does not grant authority; Miso verifies its own configured audience and the
registered identity. Do not use SDK decode helpers as identity verification.

The existing success envelope's data carries protocolVersion, issuedAt, server-derived context
(installationId/applicationId/environmentId), clientId, clientToken,
clientTokenExpiresAt, configuration, refreshAfter and expiresAt. Timestamps are UTC
ISO-8601. There is **no clientSecret**. The client ID is returned for SDK compatibility;
normal auth uses only the Miso application token. Miso 227.4 defines the accepted
target; its implementing controller OpenAPI will be the executable wire authority;
share identical sanitized fixtures across SDKs. Endpoint and helper are not yet shipped.
Existing ordinary Bearer-transport plans remain separate; never send the Entra token
as a Miso token to normal APIs. Do not reimplement token signing or identity binding.

## Same application code in local and Azure modes

The user requires the identical initSecrets()/init_secrets() call and runtime API in
local development and Azure. Applications must not branch on deployment mode.
Provider selection belongs inside the SDK:

| MISO_AUTH_MODE           | Source                                                       | Authentication                                              |
| ------------------------ | ------------------------------------------------------------ | ----------------------------------------------------------- |
| unset or `local`         | Existing process environment and normal local `.env` loading | Existing configured Miso client credentials/token flow      |
| `azure-managed-identity` | Miso bootstrap broker                                        | Azure managed identity followed by a short-lived Miso token |

For local use, reuse the existing config loader's `.env` behavior and environment
precedence (already-set environment wins over dotenv defaults), including existing
MISO_CLIENTID/MISO_CLIENTSECRET and underscore aliases. MISO_BOOTSTRAP_AUDIENCE is
not required locally. The helper creates the ordinary initialized SDK client and
exposes runtime secrets through the same require/get accessors using the local
configuration source. No Azure dependency, metadata call or bootstrap API request is
needed locally. Missing required local authentication values fail with safe errors.

Both providers expose the same runtime.client, runtime.context, runtime.secrets and
awaitable runtime.close() API. Local context, when needed, is resolved through the
existing authenticated server context flow; locally editable application/environment
values do not become authorization claims. Until context is verified, represent it as
unavailable rather than manufacture a trusted context. APIs remain server-authorized.

The local provider reads a startup snapshot; editing `.env` requires explicit restart/
reinitialization in this version. Ordinary SDK token renewal continues through its
existing local auth path. Local mode has no Entra refresh loop or broker-issued
configuration expiry. The Azure provider retains broker refresh/expiry semantics.
Provider differences must not require application-specific startup/auth branches.

Local `.env` secrets are an explicit development exception to the Azure prohibition
on resolved secrets in environment variables. Local tests must not claim the input
environment or its inherited child environment contains no secrets. Both providers
must prevent new secret persistence, diagnostic leaks and writes of resolved remote
values into the environment; ordinary local dotenv hydration remains supported.

Managed-identity mode never falls back to local after a failure and must not read
legacy credentials even if present. Azure deployment explicitly injects the mode and
removes legacy credentials. Changing mode cannot forge managed identity or registered
context; local credentials, if deliberately supplied, have only their own server-side
permissions. Do not describe a client-side mode setting as a security boundary.

Future Docker secret delivery can implement the same internal provider interface
without changing application code. No Docker provider, token protocol, auto-detection,
secret mount or new accepted mode value is implemented by this plan. Docker may use
the existing local/env provider today; a future broker/mounted-secret provider requires
its own trust, lifecycle and validation contract.

## Deployment-owned selection and fixed v1 policy

Miso processes application.json plus the trusted effective deployment configuration,
confirms the Azure identity and injects MISO_AUTH_MODE, MISO_BOOTSTRAP_AUDIENCE and
MISO_CONTROLLER_URL. The SDK consumes them internally; applications do not inspect
managed identity, choose audiences or register/select context. An Azure workload
without identity fails deployment, never downgrades to local. Local `.env` keeps the
same application code. Caller edits cannot modify Miso's server-side identity binding.

The authoritative numerical/schema/runtime contract is now **227.4, Concrete v1
schema, timing and failure policy**. It replaces previous deferred lifetime/interface
questions. Implement it exactly, with shared fixtures rather than SDK-specific defaults:

- Token 300s, snapshot 900s, refresh jitter 110–120s after issuedAt; 30s maximum clock
  difference and 30s early SDK deadlines, with monotonic protection and no server
  Miso-token expiry grace. issuedAt is now required response data.
- Fresh active-registration check on every Miso authorization, no positive cache;
  failure closed, next check after disable rejects. No claim of downstream password
  revocation or cancellation of operations already authorized.
- SDK denial invalidates all cached token/snapshot paths; token-only expiry blocks
  Miso calls, snapshot expiry blocks secret reads. Changed context/protocol errors
  invalidate. No legacy credential fallback or automatic replay of denied tokens.
- 30s total bootstrap deadline, 5s per HTTP/identity attempt, max 3 HTTP attempts,
  retry jitter [0,1]/[0,2]s, Retry-After max 10s, retries only on network timeout/
  connection failure and 429/502/503/504, one refresh cycle per 30s after failure.
- Decoded response max 1 MiB, 256 config keys, string values max 65536 UTF-8 bytes;
  strict data schema, no duplicate/unknown members, clientSecret or auth/config override.
- Change subscription returns unsubscribe; callbacks are synchronous, ordered and
  names-only. Invalidation reasons: authorization-denied, snapshot-expired,
  protocol-error, closed. Use language naming conventions from 227.4.
- close is awaitable/idempotent with a 5s cleanup deadline, generation guard and
  cancellation. SDK-created resources are owned; injected resources remain caller-owned.

Deliver OpenAPI and canonical Miso tests/fixtures/bootstrap/v1 first, then consume
hash-matched fixture copies in each SDK. Fixture pairs/clock/boundaries are specified
in 227.4. Tests exercise actual normal SDK requests and token caches, not only the
bootstrap helper. Product artifacts are implementation deliverables, not evidence
claimed by this plan-only update.

## Architecture alignment and minimal integration

Target public server-only async helper: `initSecrets()`.

```typescript
const runtime = await initSecrets();
const miso = runtime.client;
const databaseUrl = runtime.secrets.require("DATABASE_URL");
```

In Azure mode the helper reads the non-secret settings, bootstraps, constructs token-only
normal SDK configuration and initializes the client. Local mode reuses the existing
`.env` configuration/authentication flow behind the identical runtime API. The application writes no Azure HTTP,
identity parsing or token-renewal code. Call once at the existing async startup boundary;
normal Miso API calls remain unchanged. Runtime exposes client, read-only context,
secrets.require(name), secrets.get(name) and awaitable close(). Secret accessors read
only the current valid in-memory snapshot; require fails for absent/expired keys.

For Mori/Dataplane/Builder API, target one startup call plus replacement of env secret
reads in the existing central config loader. Import-time reads must be deferred.
Do not implement the apparent one-line shortcut of writing resolved secrets into
process.env/os.environ. Never require the existing credential-demanding loadConfig/
load_config before Azure bootstrap. Reuse that loader inside the local provider;
preserve existing explicit constructors/loaders for compatibility.

The SDK owns Entra acquisition, initial bootstrap, Miso token renewal and snapshot
refresh. It pins context for the session; a changed response context fails closed and
requires explicit shutdown/reinitialization. Reject malformed snapshots, missing
required token data and inconsistent timestamps. Refresh before the earliest token or
snapshot deadline, with concurrency coalescing. Authorization denial invalidates the
runtime; transient failures can use only still-valid state. Close cancels timers/tasks
and owned connections. Do not promise secure zeroization of managed-language strings.

For non-Miso application tokens and permitted runtime secrets, atomically replace the secret snapshot and issue a
secret-name-only change notification so the application's existing connection factory
can rebuild affected database/Redis clients. No secrets in notifications, no hidden
readonly-config mutation and no environment/disk/Redis-cache persistence.

Keep Azure adapters and secret-bearing bootstrap out of browser entrypoints/bundles.

### Accepted decisions and remaining dependencies

227.4 and Python 50.0 now agree on `{ protocolVersion: 1 }` as the entire request,
server-derived immutable context, `clientToken` rather than `clientSecret`, and the
SDK-owned `initSecrets()` runtime. Lifecycle ownership is resolved; do not retain the
previous one-shot `bootstrapClientConfig` design or caller app/environment selectors.

- **Shared security policy still open:** 227.4 explicitly defers concrete token/snapshot
  lifetimes, refresh defaults and bounded revocation propagation. Record these with
  timestamp validation/skew semantics and Python parity fixtures before approving
  wire/lifecycle implementation. Require `refreshAfter` before both usable deadlines;
  never extend a server deadline to compensate for clock skew.
- **Controller delivery dependency:** the route is not yet present in controller source
  or OpenAPI. Absence of implementation alone is not a defect in a future-work plan.
  Record the accepted OpenAPI envelope/configuration schema and fixtures before SDK
  wire implementation, and actual controller/registration evidence before live proof.
  Do not revive the previous client-secret/selector contract while waiting.
- **SDK implementation decisions:** use a dedicated `./bootstrap` Node-only subpath
  exporting `initSecrets`, with no root-barrel re-export. Load the local config loader
  only after local mode selection and the optional Azure adapter only in Azure mode.
  Add package-resolution proof. Verify supported Node/Azure dependency versions at
  implementation; no package compatibility or release support is claimed here.
- **Bounded transport:** record timeout, size cap, retry count, Retry-After cap and
  jitter parameters with fixtures. Retry only transient failures within the overall
  deadline; do not retry denials or unsupported protocol. These are SDK tasks, not
  reasons to redesign the accepted controller authentication contract.

### Existing initialization constraints

`src/utils/config-loader.ts` currently requires client ID and secret and imports
`dotenv/config` at module load. Local mode reuses this exact supported path, including
aliases; do not claim this loader already supports environment-only token auth.
Existing explicit token-config constructors remain compatible. Any new local token
configuration support must be explicit and tested, not silently inferred.

The privileged entrypoint must avoid `src/index.ts`/`src/sdk-exports.ts` at runtime:
those barrels export the config loader. Select mode from deployment process settings
before importing the local loader; Azure mode must not hydrate `.env` or inspect
legacy credentials. An unset mode selects local even on Azure; deployment owns
injecting the explicit Azure mode. Local `.env` loading cannot retroactively switch
an already selected provider. Test poisoned `.env` inputs in a fresh process.

`InternalHttpClient.getClientToken()` returns cached tokens before invoking
`onClientTokenRefresh`. Reusing that callback alone cannot invalidate a runtime on
background broker denial, context change or close. Add an opt-in bootstrap-session
validity boundary before request dispatch, including cached-token and logging paths;
legacy clients without that boundary retain current behavior. Cover every transport
owned by the runtime, clear owned cached tokens and prevent late refresh resurrection.
`MisoClient.disconnect()` currently disconnects Redis; it does not disable API calls.
Runtime close must also cancel broker work/timers and disable subsequent runtime use.
Do not promise to revoke requests already sent or credentials copied by consumers.

`refreshClientTokenFromCallback()` subtracts 30 seconds and token validity checks use
another 60-second buffer. Adapt broker absolute expiry without extending it or
creating a short-TTL refresh loop; test boundaries against the shared lifetime policy.
Keep Miso token renewal on the existing hook plus the explicit session guard; do not
mutate readonly config or fall back to a Miso secret grant.

## Implementation plan

### 1. Define bootstrap-only types and public entrypoint

Additional implementation best-practices to apply:

- Keep bootstrap input separate from normal config; send only protocolVersion.
  Pin server-returned context at first success and reject changed context thereafter;
  reject incompatible protocol, missing token fields and expired snapshots.
- Centralize the endpoint constant and wire fixtures; keep public exports server-only.
- Expected seams: focused `src/bootstrap/` transport, validation and lifecycle helpers,
  `package.json` export/dependency metadata, and matching unit tests. Preserve root
  exports and existing normal auth paths; confirm final filenames before coding.

### 2. Implement local provider and shared mode selection

- Keep application startup identical through `initSecrets()` and the runtime API.
- Select local for unset/`local`, Azure for `azure-managed-identity`, reject unknown
  modes. Preserve local dotenv precedence and aliases without Azure imports/calls.
- Snapshot local runtime values at startup; represent unverified local context as
  unavailable. Never fabricate context from local selectors. Reinitialization reads
  updated local configuration; normal local token renewal remains unchanged.
- Define typed require/get, close and secret-name subscription interfaces shared by
  both providers; get may return undefined only for an absent optional key in a valid
  runtime. Expired/denied/closed access fails safely rather than looking optional.
- Local snapshots have no broker expiry or background secret-change events; close is
  awaitable/idempotent in both modes. Notifications carry names only, subscriptions
  have an unsubscribe operation, and listener failures cannot leak values or corrupt
  the committed snapshot. Final signatures belong to public-api-packaging.

### 3. Acquire identity and request the Azure token snapshot

Additional implementation best-practices to apply:

- Use an async managed-identity token provider for the configured bootstrap audience;
  send the token only to the configured HTTPS Miso endpoint, with redirects disabled.
- Bypass normal token interceptors and authenticated logging to avoid recursion;
  suppress body/header capture before errors or telemetry can serialize them.
- Bound timeout, response size and retries; retry only transient failures with jitter
  and Retry-After handling, never loop on 401/403 or unsupported protocol.

### 4. Manage the in-memory snapshot and token-only client

Additional implementation best-practices to apply:

- Refresh via Entra before refreshAfter/expiry and share concurrent refresh work.
  Explicit denial invalidates the snapshot; transient failure may reuse only an
  unexpired snapshot. Cold-start failure blocks initialization.
- In Azure mode never write process environment, dotenv, disk/Redis caches, subprocess credentials
  or serialized logs; release references on disposal without claiming guaranteed
  secure erasure in a managed runtime.
- Reject late responses from an earlier refresh generation after denial/disposal;
  disposal cancels timers/in-flight work and cannot be undone by a pending response.
  State transitions and deadline checks must cover cold, valid, refreshing,
  denied/expired and disposed states with an injected clock for tests.
- Validate and map only approved configuration keys; do not spread arbitrary broker
  configuration over controller URL, auth strategy, headers or logging options.
- Atomically replace the private secret snapshot and emit changed/removed key names.
  Keep runtime.client stable through token renewal; owning application connection
  factories rebuild affected database/Redis clients. No replacement raw config API
  or hidden mutation of readonly SDK configuration is introduced.
- Enforce the session validity boundary identified above before cached-token requests;
  broker denial/context change invalidates the whole runtime. A transient failure
  permits only the token/snapshot operations whose independent deadlines remain valid.
  Close and failed initialization clean up all partially created owned resources.

### 5. Prove parity and deliver consumer guidance

Additional implementation best-practices to apply:

- In Azure mode test a fresh process without MISO_CLIENTID/MISO_CLIENTSECRET and assert bootstrap
  completes before normal token fetch, Redis, database and SDK initialization.
  Use mocked construction-order tests in the unit gate; a separate process smoke
  harness proves startup isolation without depending on Jest module cache state.
- Use synthetic sentinel credentials in success and failure capture tests; do not
  forward raw transport error objects containing headers or response bodies.
- Document compatibility/version gates and the consumer's startup and restart hooks;
  a package upgrade alone does not migrate import-time application configuration.
- Update `docs/configuration.md`, `docs/authentication.md`, `docs/quick-start.md`,
  and a focused `docs/managed-identity-bootstrap.md` guide linked from `docs/README.md`.
  Include opt-in import/adapter setup, safe diagnostics, expiry/denial shutdown and
  rebuild hooks; document that caller-owned returned credentials remain confidential.
